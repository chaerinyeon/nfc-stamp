## A. 보고 개요

**서비스 목적과 대상 (자료 미확인)**
사업계획서 V1의 서비스 목적/타겟 고객 정의는 확인하지 못했습니다. 코드 수준에서 확인되는 목적은: 동네 제휴 매장들이 **NFC 태그 또는 QR 코드**로 고객의 스탬프를 적립해주고, 목표 개수를 채우면 **쿠폰을 자동 발급**하는 디지털 적립 서비스입니다.

**이번 보고서의 검토 범위와 기준일**
- 기준일: 2026-09-15
- 검토 범위: `github.com/chaerinyeon/nfc-stamp` 저장소의 `main` 브랜치, 커밋 `645d376`(최신) 기준 코드 전체
- 검증 환경: GitHub Pages 배포본(`https://chaerinyeon.github.io/nfc-stamp/app-standalone.html`) + Supabase 프로젝트(`rkzqlzhcxixoqstajlgn`, 실 운영 프로젝트가 아닌 개발/시연용으로 추정)

**참고한 문서·코드 버전·검증 환경**
| 자료 | 상태 |
|---|---|
| V1 사업계획서 | 자료 미확인 (접근 불가) |
| 동네한바퀴 V1 개발 검토 및 수정 제안 | 자료 미확인 (접근 불가) |
| 코드·마이그레이션(`supabase/schema.sql`, `db.js`, `app.js`, `admin.js`) | ✅ 확인함 (본 문서의 1차 근거) |
| 현재 화면(GitHub Pages 배포본) | ✅ 확인함 (Playwright로 직접 조작) |
| 테스트 결과·개발 보고서(기존 문서) | 자료 미확인 (접근 불가) — 단, 이번 대화 중 직접 실행한 검증은 "실행 검증"으로 별도 표기 |

**현재 구현 범위 (한 줄 요약)**
고객 등록 → 매장 QR/NFC 접속 → 참여한 적립 프로그램에 자동 스탬프 적립(서버 즉시 처리, 승인 대기 없음) → 목표 단계 도달 시 쿠폰 자동 발급 → 매장(점주) 화면에서 쿠폰 수동 "사용 처리". **구매 확인, 정산, 취소 워크플로우, 광고 관리, 앱(네이티브), 실시간 구독은 코드에 존재하지 않습니다.**

**주요 미결정 사항 (자료 미확인 영역 포함)**
1. 점주와 매장 직원의 권한 분리 여부 (현재 코드는 매장당 비밀번호 1개만 존재 — 구분 없음)
2. "구매 확인 → 점주 승인" 단계가 사업계획서에 있는지 (현재 코드는 승인 없이 즉시 자동 적립)
3. 정산(분담금·보전) 개념 도입 여부 (현재 코드에 전혀 없음)
4. 앱(네이티브) 전환 여부 (현재 100% 웹, PWA manifest도 없음)
5. NFC 등록을 앱 내에서 처리할지 여부 (현재는 태그 읽기만 가능, 쓰기/등록 기능 없음 — 외부 앱으로 태그에 URL을 기록해야 함)

## B. 역할과 권한

> 코드에 실제로 존재하는 역할만 "구현됨"으로 표시하고, 사업계획서에 있을 수 있는 역할은 구분해 표시합니다.

| 역할 | 구현 상태 | 이용 목적 | 접근 화면 | 조회 가능 정보 | 실행 가능 작업 | 제한 사항 |
|---|---|---|---|---|---|---|
| 비로그인 방문자 | 구현됨 | 최초 진입, 등록 | U1(온보딩) | 없음 | 이름/전화번호 뒤 4자리로 등록 | 등록 전 어떤 조회·적립도 불가 |
| 로그인 고객 | 구현됨 | 적립/쿠폰 사용 | U1~U9 | **본인** 적립판·적립내역·쿠폰만 조회 (서버 RLS가 아닌 클라이언트 필터링 — 아래 참고) | 프로그램 참여, 스탬프 적립 트리거, 쿠폰함 열람 | 본인 인증은 기기 로컬 저장 아이디 기반(진짜 로그인/비밀번호 없음) — 기기 변경 시 새 사용자로 인식됨 |
| 점주 (매장 관리자) | **부분 구현** — "점주"라는 명시적 역할명은 없고 "매장 관리자" 로그인으로 구현 | 자기 매장 운영 | S1(로그인)→S5~S8 | 자기 매장 정보, 자기 매장 적립 내역, 전체 고객의 "사용 가능" 쿠폰(사용 처리용) | 매장 정보 수정, 운영중지, 비밀번호 변경, 쿠폰 사용 처리 | ⚠️ 쿠폰 사용 처리 시 **다른 매장에서 발급된 쿠폰도 조회·처리 가능** (매장 소속 쿠폰만 필터링하는 로직 없음) — 정책 미정 |
| 매장 직원 | **미구현** | (자료 미확인) | 없음 | 없음 | 없음 | 현재는 매장 비밀번호를 아는 사람 = 점주와 동일 권한. 점주/직원 구분 불가 |
| 플랫폼 운영자 | **부분 구현** — 별도 화면군 없이 "총괄 관리자" 로그인이 겸함 | 전체 매장·프로그램 관리 | S1(로그인, 총괄 모드)→S2~S4, S6~S8(전체 범위) | 전체 매장/프로그램/사용자/쿠폰/통계 | 매장·프로그램 CRUD, 전체 쿠폰 사용 처리, 초기화, 설정 변경 | 감사 로그 없음, 세분화된 운영자 권한(읽기전용 등) 없음 |
| 자동 처리 시스템 | 구현됨 | 적립/발급 규칙의 원자적 처리 | 없음(서버 함수) | — | `app_add_stamp`, `app_join_program` 등 Postgres 함수가 쿨다운 검사·적립·단계 도달 판정·쿠폰 발급을 서버에서 트랜잭션으로 처리 | 비밀번호 검증(`admin_login_*`, `_verify_store_or_master`)도 전부 서버 함수에서만 수행 |

**핵심 확인 사항**
- 고객은 본인 데이터만 조회하는가? → **부분적으로만 그렇습니다.** 화면상에서는 로그인한 사용자 ID로 필터링해 보여주지만, Supabase 테이블 자체는 `select` 정책이 `true`(전체 공개 읽기)라서, 클라이언트 코드를 우회하면 다른 사용자의 데이터도 읽을 수 있는 구조입니다. **보안/정책 결정이 필요합니다.**
- 점주/직원은 소속 매장 거래만 처리하는가? → 매장 **정보** 수정은 자기 매장으로 제한되지만, **쿠폰 사용 처리 화면은 전체 쿠폰 목록에서 매장을 선택하는 구조**라 다른 매장 쿠폰도 사용 처리 가능한 상태입니다.
- 취소 요청/확정 주체 → **기능 자체가 코드에 없습니다.**
- 정산 명세 발행/확인/이의신청/지급 기록 → **기능 자체가 코드에 없습니다.**
- 운영자 전용 화면이 없는데 실제 운영 수단은? → 현재는 "총괄 관리자" 로그인(고객용 앱과 같은 도메인의 `#admin` 화면)이 유일한 운영 수단이며, 그 외에는 Supabase 대시보드(SQL 콘솔)에 직접 접속해 데이터를 조작하는 방법뿐입니다. **이것을 완성된 운영자 UI로 간주해서는 안 됩니다.**

## C. 전체 화면 구조와 이동 흐름

> ID 체계: 요청하신 대로 U(고객)/S(매장)/C(공통) 계열을 사용합니다. **O(운영자) 계열 화면은 코드에 존재하지 않아 부여하지 않았습니다** (총괄 관리자 화면은 S 계열에 포함해 표시, scope=전체).
> 기존에 부여된 화면 ID가 코드/문서에 없었으므로, 아래 ID는 **이번 보고서에서 새로 부여**한 것입니다.

### 고객 화면 (U 계열)

| 화면 ID | 화면명 | 역할 | 웹·앱 지원 | 진입 경로 | 주요 기능 | 구현 상태 |
|---|---|---|---|---|---|---|
| U1 | 온보딩/등록 | 비로그인 방문자 | 웹만 | 최초 접속, 로그아웃 후 재접속 | 이름+전화번호 뒤 4자리로 사용자 생성 | 코드 확인 + 실행 검증 |
| U2 | 홈(내 적립판) | 로그인 고객 | 웹만 | 등록 완료 후, 탭 이동 | 도장 받기 CTA, 매장 접속 배너, 참여 프로그램별 적립판, 최근 적립 요약 | 코드 확인 + 실행 검증 |
| U3 | 프로그램 찾기 | 로그인 고객 | 웹만 | 하단 탭 | 전체 활성 프로그램 열람·참여 | 코드 확인 + 실행 검증 |
| U4 | 적립 내역 | 로그인 고객 | 웹만 | 하단 탭 | 전체 적립 이벤트 목록(최신순) | 코드 확인 + 실행 검증 |
| U5 | 쿠폰함 | 로그인 고객 | 웹만 | 하단 탭 | 보유 쿠폰(사용가능/완료/만료) 목록, 프로그램·단계 정보 표시 | 코드 확인 + 실행 검증 |
| U6 | 도장 받기 선택 모달 | 로그인 고객 | 웹만 | U2의 "도장 받기" 버튼 | QR 스캔 / NFC 태그 중 선택 | 코드 확인 + 실행 검증(QR/NFC 자체는 카메라·NFC 하드웨어 필요해 이번 세션에서 직접 검증 못함 — 버튼 클릭 후 `#btnStamp` 경유 흐름만 검증) |
| U7 | QR 스캐너 오버레이 | 로그인 고객 | 웹만(모바일 카메라 필요) | U6에서 QR 선택 | 카메라로 매장 QR 인식 → store 값 추출 | 코드 확인 (실기기 카메라 필요해 이번 세션 미검증) |
| U8 | NFC 대기 오버레이 | 로그인 고객 | 웹만(Web NFC 지원 기기) | U6에서 NFC 선택 | NFC 태그 인식 → store 값 추출 | 코드 확인 (실기기 NFC 필요해 이번 세션 미검증) |
| U9 | 사용자 메뉴 모달 | 로그인 고객 | 웹만 | U2 상단 "관리" 버튼 | 사용자 변경(로그아웃), 관리자 화면 이동 | 코드 확인 + 실행 검증 |

### 매장/총괄 화면 (S 계열 — 점주 범위와 총괄 범위를 하나의 로그인 체계로 구현)

| 화면 ID | 화면명 | 역할 | 웹·앱 지원 | 진입 경로 | 주요 기능 | 구현 상태 |
|---|---|---|---|---|---|---|
| S1 | 관리자 로그인 | 점주 / 총괄 관리자 | 웹만 | `#admin` 진입, 로그아웃 후 재접속 | 총괄/매장 모드 선택 후 비밀번호 로그인 (서버 함수로 검증) | 코드 확인 + 실행 검증 |
| S2 | 대시보드 | 총괄 관리자 전용 | 웹만 | 로그인 후 기본 탭 | 전체 통계, 운영 설정(목표 스탬프 수 등 — 현재 프로그램 도입 후 의미 축소), 총괄 비밀번호 변경 | 코드 확인 + 실행 검증 |
| S3 | 프로그램 관리 | 총괄 관리자 전용 | 웹만 | 로그인 후 탭 이동 | 적립 프로그램(캠페인) CRUD, 참여자·발급쿠폰 통계, 활성/비활성 전환 | 코드 확인 + 실행 검증 |
| S4 | 매장 관리 | 총괄 관리자 전용 | 웹만 | 탭 이동 | 매장 추가/정보수정/운영중지, QR 생성, 매장별 비밀번호 설정 | 코드 확인 + 실행 검증 |
| S5 | 내 매장 | 점주(매장 관리자) 전용 | 웹만 | 매장 계정 로그인 시 기본 탭 | 자기 매장 정보 수정/운영중지, 비밀번호 변경, QR | 코드 확인 (이번 세션에서 매장 계정 로그인 자체는 미검증 — 총괄 계정으로만 검증) |
| S6 | 적립 내역 | 점주 / 총괄 | 웹만 | 탭 이동 | 점주는 자기 매장만, 총괄은 전체 | 코드 확인 + 실행 검증(총괄 기준) |
| S7 | 쿠폰 관리(사용 처리) | 점주 / 총괄 | 웹만 | 탭 이동 | 쿠폰 목록, 사용 처리(매장 선택 후 확정) | 코드 확인 + 실행 검증(총괄 기준) |
| S8 | 초기화 | 총괄 관리자 전용 | 웹만 | 탭 이동 | 테스트 데이터 초기화 / 공장 초기화 | 코드 확인 (실제 실행은 검증 데이터 보존을 위해 이번 세션에서 실행하지 않음) |

### 공통 (C 계열)

| 화면 ID | 화면명 | 설명 | 구현 상태 |
|---|---|---|---|
| C1 | 해시 라우터 | `#admin` 유무로 고객/관리자 화면 전환 (단일 파일 버전 기준) | 코드 확인 |
| C2 | 토스트/모달 | 공통 알림·확인 다이얼로그 컴포넌트 | 코드 확인 + 실행 검증 |

### 이동 흐름 메모
- **로그인 전후 이동**: U1(미등록) → 등록 성공 시 U2. 로그아웃(U9에서 "사용자 변경")은 로컬 저장 아이디만 삭제하고 다시 U1로.
- **뒤로 가기**: 브라우저 히스토리는 관리자 해시 라우팅(`toUser`/`toAdmin`)에만 `history.pushState` 사용. 고객 화면 내 탭 전환은 URL 변경 없이 DOM 토글만 사용 → **브라우저 뒤로가기로 탭을 되돌릴 수 없음** (정책 미정 사항으로 기록 필요).
- **실패 후 복귀**: 스탬프 실패(쿨다운/미참여 등)는 토스트만 띄우고 같은 화면에 머무름. 별도 오류 화면 없음.
- **앱 설치 후 매장 복귀**: **자료 미확인/미구현** — PWA manifest가 없어 "앱 설치" 개념 자체가 없음. `?store=` 쿼리 파라미터로 재접속 시 배너가 다시 뜨는 정도만 확인됨.

## D. 화면별 상세 설명

> 전체 17개 화면을 모두 12개 항목씩 상세히 쓰면 문서가 지나치게 길어져, **핵심 화면 3개(U2, U6~U8 스탬프 적립 경로, S1)** 는 요청하신 12개 항목을 전부 채워 작성하고, 나머지 화면은 위 C절 표 수준으로 갈음합니다. Figma 작성 시 이 3개를 "상세 프레임" 템플릿으로 삼아 나머지 화면에도 동일 양식을 복제하는 것을 권장합니다.

### U2 — 홈(내 적립판)

1. **화면 ID/명**: U2 / 홈
2. **역할/목적**: 로그인 고객. 참여 중인 모든 적립 프로그램의 진행 상황을 한눈에 보고, 스탬프를 적립하는 진입점.
3. **진입 조건/이전 화면**: 등록 완료 직후(U1→U2) 또는 하단 탭 "홈" 클릭. `?store=` 파라미터가 있으면 매장 배너가 추가로 표시됨.
4. **주요 영역/표시 데이터**:
   - 상단 앱바: 로그인한 사용자 이름
   - (조건부) 매장 접속 배너: 매장명, 카테고리, 참여 중/미참여 프로그램 목록
   - "도장 받기" 히어로 버튼(이번 보고서 작성 직전 요청으로 크게 강조됨)
   - "내 적립판 (N)": 참여 프로그램별 카드 — 현재 개수, 단계별 뱃지(달성✅/도달가능/미도달)
   - "최근 적립": 최근 4건 적립 이벤트
5. **입력 필드**: 없음(버튼/클릭 위주)
6. **버튼별 실행 작업**:
   - "스탬프 적립하기"(`#btnStamp`, 매장 배너 내): 클릭 → `DB.addStamp(userId, storeId)` 호출 → Supabase RPC `app_add_stamp` 실행 → 서버가 사용자·매장·쿨다운·참여 프로그램을 검증하고 `program_wallet`/`stamp_events`/`coupons`를 갱신 → 결과(JSON)를 받아 화면 재렌더링 + 토스트/축하 모달 표시
   - "도장 받기"(`#btnCollect`): 클릭 → QR/NFC 선택 모달(U6) 오픈 → 결과로 얻은 store 값을 위와 동일한 흐름(`commitStamp`)으로 전달
   - 프로그램 카드의 "참여하기"(매장 배너 내 미참여 프로그램용): 클릭 → `DB.joinProgram` → RPC `app_join_program` 실행 → `user_programs`/`program_wallet` 행 생성 → 화면 재렌더링
7. **성공 후 이동**: 같은 화면(U2) 내 재렌더링. 쿠폰이 새로 발급되면 축하 모달에서 "쿠폰함 보기" 클릭 시 U5로 전환.
8. **로딩/빈 상태/오류/권한없음/만료**:
   - 로딩 상태 표시 스피너 **없음**(비동기 대기 중 버튼이 disabled 되는 정도)
   - 빈 상태: 참여 프로그램 0개 시 안내 카드 표시(코드 확인)
   - 오류: 네트워크 실패 시 "네트워크 오류가 발생했어요" 토스트. 매장 미등록/운영중지/미참여 프로그램/쿨다운은 서버가 반환한 메시지를 그대로 토스트로 표시
   - 만료 상태: 해당 없음(이 화면 자체에 만료 개념 없음, 쿠폰 만료는 U5에서 처리)
9. **조회/변경 데이터**:
   - 조회: `stores`, `programs`+`program_stores`+`program_tiers`(조합), `user_programs`, `program_wallet`, `stamp_events`
   - 변경(버튼 클�릭 시): `program_wallet.current_count`/`issued_tier_thresholds`, `stamp_events`(insert), `coupons`(조건부 insert), `user_programs`(참여 시 insert)
10. **실시간/새로고침**: **실시간 구독 없음.** 모든 갱신은 액션 직후 해당 함수들을 다시 호출해 수동으로 다시 그리는 방식(수동 재조회이지 Realtime 구독이 아님).
11. **구현 상태/근거**: 코드 확인(`app.js` `renderHome`, `storeBannerHTML`, `commitStamp`) + 실행 검증(이번 세션 Playwright로 참여→적립→쿠폰 발급까지 실제 확인).
12. **정책 미정/수정 필요**: 점주의 "구매 확인" 절차 없이 고객이 버튼만 누르면 즉시 적립됨 — 부정 사용(같은 사람이 여러 번 누르는 것) 방지가 쿨다운(시간 제한)뿐이라 정책 결정 필요.

### U6~U8 — 도장 받기 (QR/NFC 선택 → 스캔/태그)

1. **화면 ID/명**: U6(선택 모달) → U7(QR) 또는 U8(NFC)
2. **역할/목적**: 로그인 고객이 매장 URL을 얻는 두 가지 대체 경로(카메라 QR 인식, NFC 태그 인식) 제공. NFC 실물 태그를 직접 태그하는 것(가장 기본 경로)은 화면이 아니라 **브라우저가 URL을 여는 것**이라 별도 화면 없음.
3. **진입 조건**: U2에서 "도장 받기" 클릭(U6), 이후 선택에 따라 U7/U8
4. **주요 영역**: U7은 카메라 프리뷰 + 스캔 프레임, U8은 NFC 대기 애니메이션
5. **입력 필드**: 없음(카메라/NFC 하드웨어 입력)
6. **버튼 실행**: 닫기(✕) → 취소(reject). 스캔/태그 인식 성공 시 자동으로 `store` 값을 파싱해 `commitStamp` 호출로 이어짐(버튼 클릭이 아닌 인식 이벤트 기반)
7. **성공 후 이동**: 오버레이 닫힘 → U2로 복귀, 적립 결과 반영
8. **오류 상태**: 카메라 권한 거부/미지원, NFC 미지원(대부분의 iOS/데스크톱 브라우저 포함), https 아닌 환경 등 각각 다른 메시지로 토스트 처리(코드 확인)
9. **조회/변경 데이터**: 이 화면 자체는 데이터 조회/변경 없음(단순 URL 파싱). 실제 변경은 U2로 돌아가 `commitStamp` 실행 시 발생
10. **실시간/새로고침**: 해당 없음
11. **구현 상태/근거**: 코드 확인(`scan.js`). **실기기 카메라/NFC 하드웨어가 필요해 이번 세션(브라우저 자동화 환경)에서는 실제 스캔 동작을 검증하지 못했습니다.** U2의 `#btnStamp` 경로(매장 배너 버튼)로 동일한 서버 로직은 검증했습니다.
12. **정책 미정**: NFC "쓰기/등록"은 이 시스템에 없고 외부 앱(NFC Tools 등)에 의존 — E-5 흐름 참조.

### S1 — 관리자 로그인

1. **화면 ID/명**: S1 / 관리자 로그인
2. **역할/목적**: 점주 또는 총괄 관리자가 인증 후 관리 화면(S2~S8)에 진입
3. **진입 조건**: `#admin` 해시 접속, 로그아웃 후 재접속
4. **주요 영역**: 총괄/매장 모드 탭, 비밀번호 입력 필드(매장 모드는 매장 선택 드롭다운 추가)
5. **입력 필드**: 비밀번호(필수), 매장 모드 시 매장 선택(필수)
6. **버튼 실행**: "로그인" 클릭 → 모드에 따라 `admin_login_master` 또는 `admin_login_store` RPC 호출(서버가 bcrypt 해시로 검증) → 성공 시 `sessionStorage`에 역할+비밀번호(평문) 저장 → S2(총괄) 또는 S5(매장)로 이동
7. **성공 후 이동**: 총괄 → S2, 매장 → S5
8. **오류 상태**: 비밀번호 오류/네트워크 오류 각각 다른 토스트. 로딩 스피너 없음(버튼 disable만).
9. **조회/변경 데이터**: 조회만(비밀번호 해시 비교), 세션 데이터는 서버에 저장되지 않고 브라우저 `sessionStorage`에만 저장
10. **실시간/새로고침**: 해당 없음
11. **구현 상태/근거**: 코드 확인 + 실행 검증(이번 세션에서 총괄 로그인/설정변경/프로그램 CRUD까지 실제 수행)
12. **정책 미정**: 세션에 **비밀번호 평문**을 저장해 매 요청마다 재전송하는 구조 — 정식 토큰 기반 인증(Supabase Auth 등)으로 교체할지 결정 필요.

## E. 핵심 업무 흐름

### 1. 도장 적립
```
[U2 or 실물 NFC/QR] → URL 접속(?store=X)
   → 매장 유효성 확인(존재/운영중 여부, 서버)
   → 로그인 여부 확인(클라이언트: localStorage 사용자ID 존재?)
      - 없으면 → U1로 안내(등록 유도)
   → 고객이 "스탬프 적립하기"/"도장 받기" 버튼 클릭 (요청 생성 = 버튼 클릭 그 자체, 별도 "요청" 레코드 없음)
   → ⚠️ 점주의 "구매 대조·확인" 단계 없음 — 서버가 즉시 자동 승인
   → 서버 검증(RPC app_add_stamp): 사용자 존재, 매장 활성, (사용자+매장+프로그램) 쿨다운
   → 통과 시: program_wallet 갱신 + stamp_events insert (프로그램별 각각)
   → 고객 화면에 결과 표시(토스트/재렌더링)
   → 목표 단계 도달 시 coupons insert (쿠폰 자동 발급) — 이 스탬프 흐름과 원자적 트랜잭션
   → 지갑(program_wallet) 갱신은 이미 위 단계에 포함, 고객 화면은 함수 재호출로 재조회
```
- **담당 역할**: 로그인 고객(트리거) + 자동 처리 시스템(검증/기록)
- **관련 화면**: U2, U6, U7, U8
- **주요 데이터 변경**: `program_wallet`, `stamp_events`, `coupons`
- **실패/예외 분기**: 미등록 사용자(NO_USER), 미등록/운영중지 매장(NO_STORE/INACTIVE_STORE), 미참여 프로그램(NO_PROGRAM), 쿨다운(COOLDOWN) — 전부 코드 확인 + 실행 검증됨
- ⚠️ **"점주의 고객 요청 대조와 구매 확인" 단계는 현재 코드에 없습니다.** 사업계획서에 이 단계가 명시돼 있다면 큰 차이점이므로 결정이 필요합니다.

### 2. 쿠폰 사용
```
[U5 쿠폰함] 고객이 사용 가능한 쿠폰 확인 → 쿠폰번호(코드) 화면에 표시(6자리)
   → (오프라인) 고객이 매장 직원에게 쿠폰번호를 말/제시
   → [S7 쿠폰 관리] 점주/총괄이 쿠폰 목록에서 해당 쿠폰 찾아 "사용 처리" 클릭
      (총괄은 사용 처리할 매장을 별도로 선택해야 함 — 점주는 자기 매장으로 고정)
   → 서버 검증(RPC admin_use_coupon): 비밀번호(점주/총괄) 재검증, 쿠폰 상태(available인지), 만료 여부
      ⚠️ "소유자 확인"은 하지 않음 — 쿠폰ID만 알면 어떤 점주 계정으로도 사용 처리 가능한 구조
   → 통과 시 coupons.status = 'used', used_at, used_store_id 기록
   → 고객/점주 화면은 다음 조회(재진입/새로고침) 시에만 갱신 반영(실시간 아님)
```
- **담당 역할**: 로그인 고객(제시) + 점주/총괄(처리) + 자동 처리 시스템(검증)
- **관련 화면**: U5, S7
- **주요 데이터 변경**: `coupons.status/used_at/used_store_id`
- **실패/예외**: 쿠폰 없음, 이미 사용됨, 만료됨(자동 만료 전환 포함), 비밀번호 오류 — 코드 확인 + 실행 검증(비밀번호 검증 로직은 코드 확인만, 실제 쿠폰 사용 처리 자체는 이번 세션에서 실행하지 않음 — 검증용 쿠폰 3장을 보존하기 위해 의도적으로 생략)
- ⚠️ **"확정 분담과 사용 매장 보전 기록"은 코드에 전혀 없습니다.** (F절 참고)

### 3. 구매 취소
```
⚠️ 전체 미구현. 관련 화면(취소 요청/취소 검토), 관련 테이블(취소 기록) 자체가 코드에 없습니다.
```
- **담당 역할**: 자료 미확인 (사업계획서 필요)
- **관련 화면**: 없음
- **주요 데이터 변경**: 없음
- 현재 `admin_use_coupon`이 "이미 사용된 쿠폰은 재사용 불가" 정도만 차단할 뿐, 적립을 취소해 스탬프를 회수하는 기능은 없습니다. 결제 자체가 이 시스템에 없어(수기 확인 방식) "구매 취소"의 정의 자체를 사업계획서와 맞춰봐야 합니다.

### 4. 정산
```
⚠️ 전체 미구현. 정산 명세, 분담금 누적, 지급 기록 관련 테이블/화면이 코드에 없습니다.
```
- 시스템이 실제 송금을 하지 않는 것은 물론(그럴 계획된 코드도 없음), **분담금을 계산하는 로직 자체가 없습니다.** 쿠폰 발급 시 "이 쿠폰 비용을 어느 매장이 부담하는지"를 기록하는 필드도 없습니다(다만 `source_store_id`로 "어느 매장에서 적립되어 발급됐는지"는 기록됩니다 — 이것이 비용 분담 기준이 될 수 있는지는 정책 결정 필요).

### 5. NFC 등록
```
[S4/S5 매장 관리] 관리자가 매장 URL(?store=매장ID) 확인/복사 (QR 이미지도 이 화면에서 생성)
   → ⚠️ 이 시점부터는 시스템 밖 과정: 관리자가 "NFC Tools" 등 제3자 앱으로 실물 NFC 태그에 이 URL을 기록(쓰기)
   → ⚠️ 태그를 다시 읽어 기록을 확인하는 절차도 이 시스템이 아닌 제3자 앱의 몫
   → 매장에 부착 후, 고객이 태그하면 브라우저가 그 URL을 열어 U2(매장 배너)로 진입 — 이 부분만 우리 시스템이 처리
```
- **담당 역할**: 총괄/점주(URL·QR 준비까지만) — 실제 "쓰기"는 시스템 밖
- **관련 화면**: S4(QR 생성 모달), S5(자기 매장 QR)
- **주요 데이터 변경**: 없음(태그 자체는 이 시스템의 데이터가 아님, URL만 생성)
- **실패/분실/교체**: **미구현.** 태그 분실 시 매장 ID는 그대로이므로 새 태그에 같은 URL을 다시 쓰면 되지만, 이를 안내하거나 추적하는 기능은 없습니다.
- 위 흐름은 README(`NFC 태그에 기록할 URL 예시` 절)와 코드(`qr.js`)로 확인한 내용이며, **"태그 쓰기 → 서버 등록"의 순서가 뒤바뀔 수 있는지, 서버에 태그 자체를 등록/관리하는 기능이 필요한지는 제안 사항으로만 남겨둡니다.**

## F. 데이터 구조와 데이터 흐름

### 쉬운 용어 정리 (요청하신 개념 vs 실제 구현)

| 개념 | 정의(요청 기준) | 실제 구현 매핑 |
|---|---|---|
| 도장 | 승인된 구매에 따른 적립 기록 | `stamp_events` 행 1개 = 스탬프 1회. **"승인"은 없고 클릭 즉시 서버가 자동 기록**합니다. |
| 도장판 | 혜택 목표에 대한 진행 상황 | `program_wallet` 행(사용자×프로그램별 1개) — `current_count`, `issued_tier_thresholds` |
| 쿠폰 | 목표 달성 후 발급되는 사용 가능한 혜택 | `coupons` 행. `program_id`+`tier_threshold`로 어느 프로그램의 몇 단계 보상인지 추적 |
| 예상 분담 | 쿠폰 발급 시 기록하는 예상 부담 | **미구현.** 쿠폰에 `source_store_id`(적립이 발생한 매장)만 기록, 분담액 계산·저장 없음 |
| 확정 분담·보전 | 쿠폰 사용 시 확정하는 매장별 부담/보전 | **미구현.** `used_store_id`(사용 처리한 매장)만 기록, 정산 금액 계산 없음 |

> ⚠️ 요청하신 대로, 적립(스탬프)과 쿠폰 발급/사용을 하나의 상태값으로 합치지 않았습니다 — 실제 코드도 `stamp_events`(적립 로그, 상태값 `accumulated` 고정)와 `coupons`(발급/사용 상태: `available`/`used`/`expired`)를 별도 테이블로 분리해 관리합니다. 예상 분담액 같은 금액 필드는 애초에 존재하지 않아 "고객의 현금 잔액"처럼 오해될 소지도 없습니다.

**요청하신 세부 확인 사항**
- **구매 ID 생성 주체/시점**: 구매 ID 자체가 없음. 대신 `stamp_events.id`가 적립 시점에 서버에서 생성됨.
- **요청 ID와 구매 ID의 차이**: 구분 없음(요청=적립이 한 번에 처리).
- **쿠폰에 사용된 도장의 출처 추적**: `coupons.source_store_id` + `coupons.program_id` + `coupons.tier_threshold`로 "어느 매장/프로그램/몇 단계"까지는 추적되나, **원인이 된 개별 `stamp_events` 행 목록까지 연결되지는 않습니다**(단계 도달 판정 로직상 문제는 없으나, 사후 감사 목적엔 세부 로그 조인이 필요).
- **한 도장의 중복 쿠폰 발급 방지**: `program_wallet.issued_tier_thresholds`(정수 배열)에 이미 발급한 단계 값을 기록해두고, 그 값을 다시 발급하지 않도록 서버 함수(`app_add_stamp`)에서 체크합니다. (코드 확인 + 실행 검증: 10개/20개 단계 각 1회만 발급됨을 실제 확인)
- **중복 승인/중복 쿠폰 사용 방지**: 승인 개념 자체가 없어 "중복 승인"은 해당 없음. 쿠폰 재사용은 `coupons.status`가 `used`면 서버가 거부(코드 확인).
- **취소 기록과 원본 거래 연결**: 취소 기능 자체가 없어 해당 없음.
- **광고비와 혜택 분담금의 분리**: 광고 기능 자체가 없어 해당 없음.

## G. 조회와 갱신 방식

> 기존에 공유하신 설명(“`stamp_requests`만 Realtime 구독, 나머지는 새로고침”)과 **실제 코드는 다릅니다.** 코드 전체를 검색한 결과 `stamp_requests`라는 테이블 자체가 존재하지 않고(대신 `stamp_events`), **Realtime 구독 코드는 어디에도 없습니다**(전체 텍스트 검색 결과 `channel(`, `subscribe(`, `postgres_changes` 사용 0건).

| 화면·기능 | 데이터 출처 | 최초 조회 | 실시간 구독 | 작업 후 갱신 | 수동 새로고침 | 오래된 정보 방지 |
|---|---|---|---|---|---|---|
| U2 홈(적립판) | `program_wallet`+`programs` 등 | 화면 진입 시 1회 조회 | 없음 | 스탬프 적립/참여 액션 직후 해당 함수 재호출로 재조회 | 브라우저 새로고침 시 재조회 | 없음(같은 기기 다른 탭에서 바뀐 값은 반영 안 됨) |
| U3 프로그램 찾기 | `programs`+`program_stores`+`program_tiers`+`user_programs` | 화면(탭) 최초 진입 시 1회만 조회 | 없음 | 참여 클릭 시 즉시 재조회 | **탭 전환만으로는 재조회 안 됨** — 페이지 새로고침 필요 (이번 세션에서 실제로 이 문제를 확인함: 관리자가 새 프로그램을 만든 뒤 탭만 클릭했을 땐 안 보이다가, 페이지를 새로고침한 뒤에야 보였음) | 페이지 전체 새로고침만 유효 | 없음 |
| U4 적립 내역 | `stamp_events` | 화면 최초 로드 시 1회(`renderMain`에서 전체 뷰 동시 렌더) | 없음 | 적립 액션 직후 재조회 | 새로고침 필요 | 없음 |
| U5 쿠폰함 | `coupons`+`programs` | 최초 로드 시 1회 | 없음 | 적립으로 쿠폰 발급 시 재조회. **점주가 쿠폰을 사용 처리해도 고객 화면은 자동 반영되지 않음**(재진입/새로고침 필요) | 새로고침 필요 | 클라이언트에서 만료일 지난 `available` 쿠폰을 `expired`로 즉시 표시(화면 계산), 서버 상태 자체는 다음 액션 시점에 갱신 |
| S2~S8 관리자 화면 | 각 테이블 | 탭 클릭 시 그 탭의 함수만 재조회(탭마다 온디맨드) | 없음 | 수정/삭제/활성화 직후 해당 목록 재조회 | 필요 | 없음 |

**서버 데이터 변경과 화면 갱신 구분**
- 서버(Supabase)는 액션 즉시 반영됩니다(트랜잭션 커밋).
- 화면은 **그 액션을 트리거한 사람의 화면만** 즉시 갱신되고, **다른 사용자/다른 탭의 화면은 갱신되지 않습니다.** (예: 점주가 쿠폰을 사용 처리해도 고객 화면의 쿠폰함은 자동으로 "사용 완료"로 바뀌지 않음 — 고객이 직접 새로고침해야 함)
- 적립 요청이 "실시간으로 승인 상태"가 되는 것 자체가 이 시스템엔 없습니다(승인 단계가 없으므로). 다만 위와 같은 이유로 **지갑이 실시간으로 자동 갱신되는 것도 아닙니다.**

**로그아웃/계정 전환/매장 전환 시 정리 여부**
- 고객: `localStorage`의 사용자 ID만 삭제(`setCurrentUserId(null)`). 구독이 없으므로 "구독 해제" 자체가 불필요.
- 관리자: `sessionStorage`의 세션(역할+비밀번호) 삭제. 마찬가지로 구독 없음.
- **결론**: 실시간 구독이 없어 "정리가 안 되는" 문제 자체가 발생하지 않지만, 반대로 **다른 사람의 최신 상태를 보려면 항상 수동 새로고침이 필요하다는 한계**가 있습니다. 이는 정책/우선순위 결정이 필요한 부분입니다(예: 매장 직원용 화면만이라도 Realtime 도입 여부).

## 최종 확인 관련 메모

이 문서는 Figma 프레임이 아니므로 "글자 잘림/겹침/색상 상태 표시" 같은 시각 검수는 적용되지 않습니다. Figma로 옮길 때 아래를 유지해 주세요:
- 상태 표시는 항상 **색상 + 텍스트**를 함께 사용 (예: 초록 배지 "실행 검증", 회색 배지 "미구현", 노랑 배지 "정책 미정")
- 화면 ID(U/S/C + 숫자)는 화면 상세 프레임, C절 목록표, E절 흐름도, F절 데이터표에서 **동일하게** 사용해 서로 링크되도록 구성
- 흐름도 화살표에는 실제 동작 이름을 넣기(예: "조회", "참여 요청", "발급", "사용 처리", "재조회") — 위 E절 다이어그램의 화살표 옆 설명을 그대로 옮기면 됩니다.
